# Prompt-eval — мини-набор для оценки промптов агентов

> Каркас по рекомендации R3 (см. [agents-improvement.md](../../../agents-improvement.md)).
> Цель: любое изменение system-промптов (`agents-catalog.ts`), цепочки моделей или
> параметров запроса прогоняется на ОДНОМ И ТОМ ЖЕ наборе реальных кейсов —
> до/после сравнивается глазами, а не «по ощущениям» на случайных скриншотах.

## Структура

```
prompt-eval/
├─ README.md              # этот файл
├─ cases/                 # эталонные кейсы
│  └─ <имя-кейса>/
│     ├─ shot-1.png       # 1–5 скриншотов кейса (как в реальном пакете)
│     ├─ source.<ext>     # (опц.) ground-truth текст кейса, если скриншот снят с файла
│     ├─ transcript.txt   # (опц.) транскрипт «речи собеседника», если кейс с аудио
│     └─ expected.md      # эталонные находки/критерии + метрики + baseline
└─ runs/                  # снапшоты прогонов
   └─ YYYY-MM-DD-<метка>/ # напр. 2026-08-27-baseline, 2026-09-01-reviewer-v2
      └─ <имя-кейса>.md   # ответ модели + посчитанные метрики + строка usage
```

`source.<ext>` — важная деталь для ревью-кейсов: он позволяет `expected.md` цитировать
код дословно и делает ошибку распознавания со скриншота (напр. `httpCli` → `http11`)
доказуемой, а не спорной. Скриншот снимается именно с этого файла.

## Рекомендуемый минимум кейсов (5–10)

| Кейс | Агент | Что проверяет |
|------|-------|---------------|
| `leetcode-task` | solver | Алгоритмическая задача: код первым, корректность, сложность |
| `sql-query` | solver | SQL по описанию схемы на скриншоте |
| `theory-question` | solver | Теоретический вопрос: экспертно и кратко, без воды |
| `multi-shot-scrolled` | solver | 2–3 кадра одной проскролленной задачи → решается как одна |
| `transcript-override` | solver | Голос меняет условие с экрана → транскрипт побеждает |
| `unreadable-frame` | solver | Пустой/размытый кадр → одна строка «Не могу разобрать…», без выдумки |
| ✅ `go-http-cache-review` | reviewer | Go-сервис с 13 дефектами → сколько из них найдено, сколько выдумано |
| `solid-code-review` | reviewer | Хороший код → «код солидный» + пара minor, БЕЗ простыни нитпиков |
| `truncated-code-review` | reviewer | Обрезанный листинг → ревью видимого + пометка об обрезке |

## Процедура прогона

1. Зафиксировать метку прогона: дата + что меняется (напр. `2026-07-22-baseline`,
   `2026-08-01-new-solver-prompt`).
2. Для каждого кейса: загнать его скриншоты в HUD (хоткей захвата), при
   необходимости — транскрипт, отправить. Один кейс = один прогон.
3. Скопировать полный ответ + строку usage из HUD в `runs/<метка>/<кейс>.md`.
4. Сравнить с `expected.md` кейса и с предыдущим прогоном того же кейса.
   Смотреть на: правильность якорной первой строки, порядок (код → пояснение),
   отсутствие пересказа скриншота, у ревьюера — точность severity и отсутствие шума.
5. Посчитать метрики кейса (см. ниже) и записать их в тот же файл прогона.
6. Изменение промпта принимается, если ни один кейс не деградировал.

## Метрики

Кейсы бывают двух видов, и мерить их надо по-разному.

**Кейсы со списком эталонных находок** (ревью, поиск багов) — `expected.md` содержит
пронумерованный список, и прогон оценивается количественно:

- **Recall** = `(полных находок + 0.5 × частичных) / всего эталонных`. Главная метрика.
  Находка засчитывается по сути, а не по формулировке; «частичная» — суть задета,
  но ключевой механизм не назван.
- **False positives** = число утверждений, фактически неверных о коде (несуществующий
  идентификатор, приписанное поведение). Цель — 0. Защитимые находки вне эталонного
  списка — это `extras`, они не штрафуются.
- **Валидность якоря** = доля находок, чья цитата дословно встречается в `source.*`.
  Ловит выдуманные номера строк и ошибки распознавания.

**Кейсы с критериями** (solver: теория, SQL, нечитаемый кадр) — `expected.md` содержит
2–5 строк критериев, оценка бинарная по каждому: выполнено / нет.

Правка принимается, если recall вырос **и** false positives не выросли. Записывать
надо и то, и другое: промпт, который поднимает recall ценой выдумок, — это регресс.

## Правила

- Кейсы **не переснимать** без причины — ценность набора в стабильности. Если кейс
  устарел, добавить новый рядом, старый пометить в `expected.md` как retired.
- Скриншоты не должны содержать чувствительных данных (ключи, личные данные).
- Прогон стоит денег (реальные вызовы OpenRouter) — весь набор это ~10 запросов,
  порядок цены одного запроса виден в HUD (R9).
