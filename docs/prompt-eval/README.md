# Prompt eval — методика и запуск (R3 + R13)

Правка промпта, модели или входа принимается **только по цифрам**: взвешенный recall
вырос, false positives не выросли — на обоих кейсах, включая отложенный (held-out).
Всё остальное — гипотеза.

## Состав

```
docs/prompt-eval/
  cases/<id>/
    case.json        эталон: находки с severity, строками, происхождением
    source.*         ground-truth текст кода (с него рендерятся скриншоты)
    shots/           отрендеренные кадры + manifest.json (pnpm eval:shots)
  runs/<дата>-<label>/
    summary.md       таблица: кейс × arm, mean ± sd по повторам
    results.json     все прогоны с метриками и конфигом
    answers/<case>/  сырые ответы + *.verdict.json от судьи
eval/                код харнесса (вне приложения; Node)
```

| Кейс | Агент | Эталон | Роль |
|---|---|---|---|
| `go-http-cache-review` | reviewer | 18 находок: 13 из ответа Sonnet 5 (G1–G13) + 5 найденных при разборе baseline (X1–X5) | рабочий: по нему можно смотреть ответы |
| `py-job-worker-review` | reviewer | 14 заложенных дефектов (P1–P14) | **held-out**: ответы по нему не читаем при правке промптов |
| `solve-longest-substring` | solver (Go) | 7 критериев: алгоритм O(n), левая граница не откатывается («abba»), код на Go по заглушке, пустая строка, сложность, формат | рабочий |
| `solve-sql-carts` | solver (SQL) | 6 критериев: семантика «хотя бы один неактивный», без дублей, нужные колонки, ключи JOIN, формат, индекс | рабочий |
| `solve-go-channels-theory` | solver | 6 фактов о каналах Go (запись в закрытый, nil-канал, двойной close…) | рабочий |
| `solve-lru-cache` | solver (TS) | 7 критериев; условие разбито на **2 кадра**, ограничение «get тоже использование» — только во втором | **held-out** |
| `solve-unreadable` | solver | пустой редактор: ответ «Не могу разобрать задачу», ничего не выдумывать; только `shot` | рабочий |

Отложенные кейсы нужны потому, что 7 осей ревьюера (R12-B) выведены из промахов на первом
кейсе: проверять их только на нём — подгонка под ответ. Для solve-кейсов `findings` — это
**критерии** правильного ответа (судья получает отдельную рубрику: «выполнен / частично /
нет», ошибки в коде ответа — FP); метрики те же.

## Метрики

- **Взвешенный recall** (главная): `Σ w·coverage / Σ w`, веса Critical 3 · High 2 ·
  Medium 1 · Low 0.5, `full` = 1, `partial` = 0.5. Пропуск гонки, роняющей процесс,
  стоит в 6 раз дороже пропуска устаревшего `ioutil` — простой recall их не различал.
- **recall13** — невзвешенный recall по исходным 13 пунктам (G1–G13): сопоставимость с
  baseline 2026-08-27.
- **FP** — утверждения, фактически неверные о коде (по вердикту судьи).
- **Valid extras** — реальные дефекты вне эталона. Не штрафуются; повторяющиеся —
  кандидаты в эталон.
- **Якоря** (детерминированно, `eval/lib/scoring.ts`): «цитата» валидна, если дословно
  (с точностью до пробелов) есть в исходнике; номер строки валиден, если код-токен из той
  же строки ответа встречается в исходнике в диапазоне ±1 строка. Ссылка без код-токенов
  рядом не проверяема и не учитывается. Эвристика — смысл проверяет судья.
- **Латентность** (медиана), **стоимость** (OpenRouter `usage.cost`), **length-cut** —
  сколько ответов провайдер оборвал по длине.

Судья — LLM (`EVAL_JUDGE_MODEL`, по умолчанию Sonnet 5, temperature 0): видит
пронумерованный исходник, эталон и ответ, возвращает JSON с покрытием каждого id и
списком прочих утверждений (`valid_extra` / `false_positive` / `neutral`).

**Шум.** Одна находка — это 0.018–0.107 взвешенного recall (Low … Critical из 28). Поэтому минимум 3 повтора
на arm (по умолчанию), решение — по среднему и разбросу, а не по одному прогону.

## Запуск

```bash
pnpm eval:shots                    # один раз: рендер скриншотов (нужен Chrome/Edge
                                   # или PLAYWRIGHT_CHROMIUM_EXECUTABLE)
OPENROUTER_API_KEY=sk-or-... pnpm eval          # сетка по умолчанию
```

Без `OPENROUTER_API_KEY` тест пропускается; в `pnpm test` eval не входит.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `EVAL_CASES` | все | список id кейсов |
| `EVAL_MODELS` | `anthropic/claude-haiku-4.5,anthropic/claude-sonnet-5` | модели |
| `EVAL_INPUTS` | `text,shot` | из `text`, `shot`, `text+shot`, `shot+ocr` (скриншот + проход распознавания, P1 п. 7) |
| `EVAL_TRANSCRIBE_MODEL` | модель arm'а | модель прохода распознавания для `shot+ocr` |
| `EVAL_PROMPTS` | `current` | `current`, `main-2026-07-22` (снимок промптов до R1–R18) |
| `EVAL_SHOT_VARIANT` | `dark-13px-1568` | ключ из `shots/manifest.json` (`*-2560` — без даунскейла) |
| `EVAL_REPEATS` | `3` | повторов на arm |
| `EVAL_TEMPERATURE` | `0.3` | число или `off` |
| `EVAL_REASONING` | `off` | `low` / `medium` / `high` (снимает temperature) |
| `EVAL_JUDGE_MODEL` | `anthropic/claude-sonnet-5` | судья |
| `EVAL_JUDGE_TEMPERATURE` | `0` | число или `off` |
| `EVAL_CONCURRENCY` | `3` | параллельных прогонов |
| `EVAL_LABEL` | `grid` | суффикс каталога прогона |
| `EVAL_SCORE_DIR` | — | вместо прогона — пересчитать ответы в `<dir>/answers/<case>/*.md` |

Промпт `current` идёт через **настоящие** `AgentRunner` + `ResilientLlm` приложения;
отличается только транспорт (fetch вместо нативного `llm_stream`). Тело запроса в
`eval/lib/openrouter.ts` зеркалит `build_request_body` в
`src-tauri/src/infra/openrouter_client.rs` — при правке одного поправить второе.

## Порядок экспериментов

1. **Факторный план** (по умолчанию): {Haiku, Sonnet 5} × {text, shot}. Отвечает, что даёт
   прирост — модель или вход. Если Sonnet 5 с текстом ≈ потолок, а Haiku нет — дело в
   модели, решение — heavy-маршрут (R11).
2. `EVAL_PROMPTS=current,main-2026-07-22` — эффект правок промпта R12/R14/R18 при
   прочих равных.
3. `EVAL_REASONING=medium` на лучшей модели — даёт ли рассуждение прирост, стоящий
   латентности (R16).
4. `EVAL_SHOT_VARIANT=dark-13px-2560` против `dark-13px-1568` — цена даунскейла на
   чтении мелкого кода (R17).
5. `EVAL_INPUTS=shot,shot+ocr,text` — окупается ли проход распознавания (P1 п. 7): если
   `shot+ocr` заметно ближе к `text`, чем `shot`, — включать `VITE_AUTO_TRANSCRIBE`.
6. `pnpm models:check`, затем перед тем как ставить `VITE_HEAVY_*` в прод — один живой
   запрос в приложении (проверка, что провайдер принимает выбранные параметры).

Правило приёмки: рост взвешенного recall на **обоих** кейсах больше разброса (sd), FP не
выше, якоря не ниже.
